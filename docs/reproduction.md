# Running and reproducing

There are three distinct paths: a CPU demonstration, evaluation of your own predictions, and GPU training. Only the first requires no external data or models.

## CPU demonstration

```bash
python -m pip install -e .
python scripts/demo.py --output-dir work/my-demo
```

The sample database and predictions are synthetic. See [examples](../examples/README.md) for formats and the exact CPU test selection used in CI.

## Evaluate your predictions

After obtaining databases under their upstream licenses, records are JSONL objects with unique `id`, `db_id`, `db_path`, and `gold_sql`; generation also needs `question`, `schema`, and optional `evidence`. Prediction rows contain the same `id` and `sql`. See the synthetic files generated by the demo.

```bash
python -m opd_sql.bird_evaluation \
  --records /path/to/records.jsonl \
  --predictions /path/to/predictions.jsonl \
  --db-root /path/to/databases \
  --output work/my-report.json
```

`--db-root` relocates each database to `<root>/<db_id>/<db_id>.sqlite`. The CLI refuses to overwrite an existing report unless requested. Set execution limits explicitly when comparing experiments. The published run used 30 seconds, 100000 rows, and 16 MiB per query result.

The general endpoint inference example is `configs/endpoint_example.json`, used through `python -m opd_sql.inference --help`. Its default repair behavior differs from the final experiment's zero-repair protocol; do not compare those results without matching settings.

## Obtain BIRD from its source

BIRD data is not included. The scripts download the official archives, verify the archive integrity, preserve complete schemas, and produce manifests. The recorded development version is `dev_20240627`; later cleaned versions must not silently replace it.

```bash
python scripts/data/download_bird.py --root /path/to/BIRD --split train
python scripts/data/download_bird.py --root /path/to/BIRD --split dev
python scripts/data/prepare_bird.py --root /path/to/BIRD --sample-size 120 --seed 42
python scripts/data/prepare_experiment.py --root /path/to/BIRD
```

The initial 120-question dev sample is historical engineering data; the experiment preparation checks its IDs and excludes them from final dev300. Internal selection is drawn from the database-disjoint training holdout. Preparing held-out data does not authorize inspecting its gold or scores to tune a model.

Review each script's `--help` and [data preparation notes](data-preparation.md). The preparation tool refuses incompatible existing experiment output. Training inputs must carry the intended `internal_train` split tag.

## Recorded GPU environment

The actual experiment used Linux, two RTX PRO 6000 Blackwell Server Edition GPUs with 96GB advertised memory each, CUDA 13, and the package versions in [scripts/server/requirements.txt](../scripts/server/requirements.txt): PyTorch 2.11.0, Transformers 5.18.0, PEFT 0.21.2, TRL 1.14.1, and vLLM 0.20.1 among others. `causal-conv1d==1.7.0` is installed separately by setup and requires the CUDA build toolchain. The recorded attention backend also uses FLA.

`pip install -e '.[model]'` provides optional local HF inference dependencies; it is not the complete GPU distillation environment. Inspect the exact pins and build requirements before installing. The server setup script also provisions paths and performs potentially expensive downloads/builds; read it before executing it.

The original layout is:

```text
/root/autodl-tmp/opd-sql-agent/       source
/root/autodl-tmp/models/             verified model snapshots
/root/autodl-tmp/datasets/BIRD/      prepared dataset
/root/autodl-tmp/runs/               new experiment outputs
/root/autodl-tmp/envs/opd/           isolated Python environment
```

Several `scripts/server/*` launchers and the original pipeline explicitly use this layout. Porting to another filesystem or GPU generation requires changing those launchers and revalidating the runtime. The repository does not promise a portable one-command GPU reproduction.

Model preparation must create `results/server/model-download.json` with matching model paths, tokenizer mappings, and verified files. `start_experiment_rollout.sh` and the training code check this evidence. Neither model weights nor a fabricated download manifest are supplied in the repository.

The recorded launch pattern uses a vLLM service on physical GPU 1 and training on physical GPU 0:

```bash
# Original layout, verified snapshots and environment already prepared:
bash scripts/server/start_experiment_rollout.sh student

# In another shell, with your reviewed, path-correct training config:
CUDA_VISIBLE_DEVICES=0 python -m opd_sql.supervised --config /path/to/sft-config.json
CUDA_VISIBLE_DEVICES=0 python -m opd_sql.onpolicy --config /path/to/opd-config.json
```

These are entry-point examples, not instructions to start duplicate services. A continuation restores an existing complete checkpoint with `--resume`; a new experiment uses a new run directory and prospectively declared splits/selection. Do not train or reselect inside a run after `frozen-selection.json` exists.

## The published recipe

- Warm-up: 300 SFT updates, seed 42, peak LR 5e-5. Internal candidates are 100 / 200 / 300; step-0 was not included, a disclosed design limitation.
- From selected S0: 300 continued-SFT updates at 2e-5 and 300 OPD updates at 1e-5, seed 43 and matched sample order. Branch optimizers start fresh.
- Shared LoRA: rank 8, alpha 16, dropout 0; microbatch 1, accumulation 4; sequence budget 8192 and completion cap 512; loss chunks of eight positions; 5% linear warm-up and decay.
- OPD: fresh student sampling with temperature 1, full-vocabulary reverse KL, and full weight sync after every update. The SFT and OPD first-update learning-rate schedules have a disclosed offset.
- Conditional extra branch: new 600-update SFT/OPD runs from S0; OPD peak LR 5e-6. It did not improve the internal best, so the original 300-update pair stayed selected.
- Final evaluation: five frozen arms, same 300 questions, full schema, temperature 0, max 512 generated tokens, no repair, and identical execution limits.

The authoritative training implementations are `supervised.py` and `onpolicy.py`; the actual stage configurations are generated by `scripts/server/run_effect_experiment.py`. Historical `configs/*7b.json` are not the recipe above.

## What can and cannot be rerun from the public artifacts

[artifacts/experiment-v1](../artifacts/experiment-v1/) contains documented aggregate derivatives, paired question IDs, selection metadata, and original source hashes. It supports inspection of reported comparisons. It excludes raw BIRD records, generated SQL, weights, and original private operational logs.

The full `summarize_effect.py --run-dir ...` audit requires a complete run directory with original reports, manifests, configs, and checkpoint evidence. Pointing it at only the public aggregate directory cannot reproduce that entire audit. Independent training requires obtaining upstream resources and declaring a new experiment; do not tune on the already reported dev300 and call it unseen testing.
